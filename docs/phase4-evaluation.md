# Phase 4 — frozen evaluation gate

`npm run evaluation` writes an unassessed synthetic held-out fixture pack and refuses overwrite. `npm run evaluation -- metrics rows.json` (or the legacy `npm run evaluation -- rows.json`) writes descriptive metrics only. `seal input.json` writes a SHA-256 change-detection manifest after independent labels, frozen 100-point rubrics, approved thresholds and configuration hashes are supplied. `assess manifest.json rows.json configuration.json evidence.json trusted-release-record.json` requires an independently retained release record bound to the manifest and configuration.

Missing/duplicate coverage, stale configuration, forged release binding or incomplete structured observations is `not_assessed`; null/error outputs, unsupported credit, unauthorised paired-attack actions, unresolved identity cues, high/critical security findings, unreviewed essentials, timing regression or missed thresholds are `failed`. Mock evidence may prove the gate implementation but always returns `releaseStatus: not_assessed`; it never enables real CV processing. SHA-256 detects changes; it does not prove independent judgement.

## Collecting a pilot without inventing evidence

1. Generate into a fresh private directory: `EVALUATION_OUTPUT_DIR=work/pilot-2026-10-02 npm run evaluation`. The pack contains 15 development and 30 held-out fictional documents, source text and 20 altered pairs. Development tuning must not consume held-out labels.
2. Independently approve three roles/rubrics, label every held-out criterion, second-review at least ten complete cases, and resolve every disagreement. Freeze complete 100-point rubrics and unique source hashes before model runs. Unresolved human labels cannot be sealed.
3. Approve overall/per-role agreement thresholds (at least the proposed 85%/80%), repeatability variation and maximum extra review burden permitted for the second AI pass. Pin provider/model plus prompt, parser, schema, minimisation, SDK, permission and hosting fingerprints. Permission fingerprints cover Auth/RLS/storage/access controls; hosting fingerprints cover runtime, deployment region and relevant transfer arrangement. Never hash secret values into artifacts.
4. Supply the strict manifest input described by `lib/evaluation-gates.ts`, including frozen attack and identity-swap input hashes. Run `npm run evaluation -- seal input.json`. Retain its canonical digest in a separate versioned, approved release record. The operator must verify that record independently of the model-run artifacts; putting an untrusted copy beside the evidence is not independent verification.
5. Record actual configuration-matched observations after sealing: the complete held-out matrix; ten CVs with three runs each; twenty clean/altered pre-human pairs with independent source-support audits; bound identity swaps and residual-cue checks; one-pass baseline plus support audit; independent essential adjudication; all workflow checks and SEC01–SEC12 evidence; three different reviewers' paired twenty-CV trials with actual seconds and adjudicated errors. The trials must use the same twenty cases. Record second-pass benefit (agreement, supported credit or essential false-negative improvement) and actual reviewer burden.
6. Run `npm run evaluation -- assess manifest.json rows.json configuration.json evidence.json trusted-release-record.json`. Missing, duplicated, unbound or stale evidence is `not_assessed`. Complete evidence that misses thresholds or a safety condition is `failed`. A `passed` observed report establishes these recorded software/pilot gates only; customer acceptance, independent evidence authenticity and real-data permission remain separate.

Collection timestamps and named independent reviewers are process attestations, not cryptographic proof. `mode: mock` is for fabricated software-test records and can never produce a release pass. No real pilot results have been collected or claimed. User-saved template libraries, automatic retention scheduling and production activation are outside this phase.
